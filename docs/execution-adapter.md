# Administrative execution boundary

This is an original local laboratory scheduling adapter. It is an extension of Bring Vene's patient-controlled visit, not a healthcare scheduling service or a verified clinical order system.

The owned launcher starts `bring_vene.execution.office:app` as a separate loopback HTTP process and `bring_vene.execution.worker` as a separate consumer. Office availability, order prerequisites and receipts are persisted in Postgres. Office tables have no encounter/patient foreign keys. This prototype uses the same physical database and database role; production isolation and a real office adapter are future work.

Only an authenticated patient can allow a window lookup. The adapter receives only `morning`/`afternoon`, then a slot identifier, office availability revision, opaque request ID and sandbox order ID. It never receives names, transcripts, clinical instructions or invitation/session identifiers. Lookup scope does not authorize booking. A responsible invited clinician must explicitly confirm the visible sourced step and optionally issue a synthetic office order. Professional identity verification is not implemented by these local roles.

Approval digest binds the action ID, exact window/slot, relevant plan and evidence versions/content/audiences, current lookup grant revision, order and clinician. Restoring permission does not resurrect prior work. The approval, queued action and outbox are committed together. Worker leases use Postgres `FOR UPDATE SKIP LOCKED`; stale lease holders cannot commit a new result. Office request IDs are unique, conflicting payload reuse is rejected, and reservations serialize against persisted availability.

Dispatch linearizes at a durable `in_flight` send decision under the encounter lock. A withdrawal/correction committed before that decision prevents dispatch. Later revocation cannot recall already dispatched work. Network waits hold no encounter/media locks. Send intent survives a crash, and a lost result becomes `unknown`. Reconciliation reads the original request ID before another write; only authoritative absence and renewed current authority permit another send with the same payload and ID. Actual confirmed/rejected receipts survive later local corrections. No cancellation endpoint or automatic rebooking is claimed.

Office scenarios: normal slots, no slot, expired availability, delayed lookup (actual HTTP timeout), rejected booking, timeout after a persisted write, and duplicate receipt events. The duplicate scenario supplies two identical events in a response; authenticated asynchronous callbacks and late office delivery remain Phase 7 work. The adapter rejects conflicting duplicates and stores one receipt.

Patient-only cues quote current office status and check time. Public speech requires sharing the plan and every supporting source with everyone present, plus the existing per-participant speaking agreements. Lookup/action snapshot checks reject cues whose office result changed. Closeout can include current checks; speech is never booking authorization. Role-filtered execution APIs omit stale action details from guests even if a changed plan is subsequently shared again. Patients retain actual previous receipts to avoid pretending local edits cancel reservations.

The conversation plan remains a draft derived from its source. Verified administrative prerequisites and reservation outcomes live in the office follow-through panel. No model-generated flag creates authority, a clinical order, or a receipt. Raw audio is not recorded. Ordinary logs contain HTTP paths, opaque IDs and safe error classes, not request bodies or transcript text.

Run `scripts/check.ps1 -Phase 6` sequentially against the isolated test database. `scripts/dev.ps1` allocates the local office port and generates a process-owned office bearer token; no external office API key is required for this sandbox. All live STT/model/TTS provider checks remain separate. Missing live-provider configuration never becomes fixture success.
